DECISIONES DE ARQUITECTURA DE URBANGUARD

Documento de Registro de Decisiones de Arquitectura (ADR)
Proyecto: UrbanGuard
Área: Autenticación, Autorización, Gestión de Identidad y Multitenencia
Estado: Aprobado / Consolidado

===============================================================================
1. RESUMEN EJECUTIVO
===============================================================================

Este documento consolida las decisiones definitivas tomadas para la redefinición
de la arquitectura de seguridad, autenticación, gestión de usuarios y comunicación
inter-servicio del sistema UrbanGuard.

Se adopta un enfoque de Zero Trust distribuido, desacoplamiento estricto de
responsabilidades mediante Domain-Driven Design (DDD), y eliminación del problema
de doble escritura (Dual-Write Problem) mediante Self-Healing via JIT
(Just-In-Time / Lazy Provisioning)[cite: 1].

===============================================================================
2. MODELO DE ROLES E IDENTIDAD
===============================================================================

2.1 Proveedor de Identidad (Auth0)
- Protocolo: OAuth 2.0 + Authorization Code Flow con PKCE directamente entre
  la App Móvil y Auth0[cite: 1].
- Datos capturados en Auth0: ÚNICAMENTE correo electrónico y contraseña
  (o login social). Auth0 NO captura nombres, apellidos ni teléfonos.
- Contenido del JWT: Auth0 actúa exclusivamente como Proveedor de Identidad (IdP)[cite: 1].
  Emite tokens firmados digitalmente (JWKS) con los siguientes claims:
  * sub: Identificador único de Auth0 (userId).
  * email: Correo electrónico del usuario.
  * https://urbanguard.com/role: Custom claim con el rol global del usuario.
    Convención DEFINITIVA (Decisión UG-2026-09): el claim se nombra en inglés
    (namespace https://urbanguard.com + claim "role", NUNCA "rol" ni el dominio .co).
    Este nombre lo usan por igual la Action de Auth0, el backend que valida el
    JWT y la App Móvil para evitar desalineaciones (ver sección 7).
- Decisión de alcance: Auth0 NO almacena ni emite conjunto_id[cite: 1]. La lógica de
  pertenencia a conjuntos residenciales es 100% responsabilidad del dominio
  de negocio[cite: 1].

2.2 Jerarquía de Roles Globales
Auth0 asigna uno de los siguientes roles en el claim https://urbanguard.com/rol[cite: 1]:

- USUARIO: Usuario registrado que aún no está vinculado a ningún conjunto.
  Puede registrar un nuevo conjunto o ingresar a uno existente.
  Contexto de Conjunto: conjunto_id = null.
- RESIDENTE: Propietario o arrendatario con vinculación aprobada a una unidad
  residencial[cite: 1]. Contexto: Asociado a uno o más conjunto_id[cite: 1].
- VIGILANTE: Personal de seguridad asignado a un conjunto[cite: 1].
  Contexto: Asociado a un conjunto_id[cite: 1].
- ADMINISTRADOR: Responsable de la administración de uno o varios conjuntos[cite: 1].
  Contexto: Asociado a uno o varios conjunto_id[cite: 1].

===============================================================================
3. DELIMITACIÓN DE RESPONSABILIDADES POR COMPONENTE
===============================================================================

3.1 Auth0 (Identity Provider Externo)
- Autenticación de credenciales (Email/Password únicamente, Social Sign-In)[cite: 1].
- Gestión de contraseñas y MFA[cite: 1].
- Emisión y firma de Access Tokens (JWT) y Refresh Tokens[cite: 1].
- Asignación del rol global (USUARIO, RESIDENTE, VIGILANTE, ADMINISTRADOR)[cite: 1].

3.2 api-gateway (Spring Cloud Gateway)
- Punto único de entrada HTTP para la App Móvil[cite: 1].
- Enrutamiento de solicitudes hacia los microservicios de backend[cite: 1].
- TLS Termination y validación preliminar de tokens[cite: 1].
- Regla estricta: No contiene lógica de negocio, agregación ni transformaciones
  de dominio[cite: 1].

3.3 identity-service (Microservicio de Usuario Puro)
- Concepto: Agenda o directorio central de datos personales puros[cite: 1].
- Base de datos: user_database (PostgreSQL)[cite: 1].
- Entidad Usuario: Almacena userId (sub), email, nombres (nullable),
  apellidos (nullable), telefono (nullable), activo y timestamps[cite: 1].
- Regla de negocio de Perfil: Inicialmente los datos personales (nombres,
  apellidos, teléfono) se crean vacíos/null. El usuario puede completarlos
  de forma opcional cuando realiza el flujo de ingresar o registrar un conjunto.
- Aislamiento estricto: NO almacena rol ni conjunto_id[cite: 1].
- Integraciones: Es el único servicio con credenciales para comunicarse con la
  Management API de Auth0 cuando se requieren operaciones administrativas explícitas[cite: 1].
  No participa en el flujo de login ni en la validación de peticiones ordinarias[cite: 1].

3.4 community-service (Dominio de Negocio y Censo)
- Concepto: Dueño del dominio residencial y la multitenencia[cite: 1].
- Base de datos: community_database (PostgreSQL)[cite: 1].
- Entidades: Conjuntos residenciales, unidades habitacionales, censo de personas
  (propietarios/arrendatarios), solicitudes de vinculación (SolicitudVinculacion)
  y la relación (userId, conjunto_id, unidad_id)[cite: 1].
- Responsabilidad: Gestiona la creación de conjuntos y la aprobación de ingreso
  de usuarios de forma 100% autónoma[cite: 1].

===============================================================================
4. ESTRATEGIA DE APROVISIONAMIENTO: SELF-HEALING VIA JIT (LAZY PROVISIONING)
===============================================================================

Para resolver el riesgo de fallos parciales (Dual-Write Problem) donde un usuario
queda registrado en Auth0 pero no en identity-service (por caídas de red o del
microservicio), se adopta el patrón Self-Healing via JIT:

Flujo:
1. App Móvil realiza Login PKCE Exitoso contra Auth0.
2. Auth0 emite JWT con sub, email y rol global.
3. App Móvil consulta GET /api/users/me a identity-service a través de api-gateway.
4. identity-service consulta en user_database:
   - Si existe: Devuelve el perfil del usuario[cite: 1].
   - Si NO existe (JIT Provisioning): Extrae 'sub' y 'email' del JWT, inserta el
     registro en user_database[cite: 1] dejando nombres, apellidos y teléfono
     en NULL, y devuelve el perfil inicial recién creado.

Ventajas de esta decisión:
- Resiliencia Total: La sincronización se repara automáticamente en el primer
  login del usuario de forma transparente.
- Eliminación de Webhooks Frágiles: No se requiere exponer webhooks vulnerables
  a caídas de red desde Auth0.
- Bajo Acoplamiento: Eliminación de llamadas REST síncronas de aprovisionamiento
  durante el registro en Auth0.

5. FLUJOS DETALLADOS DEL SISTEMA
===============================================================================

5.1 Flujo A: Registro de un nuevo USUARIO (Self-Signup)
1. El usuario descarga la App Móvil e inicia el registro en Auth0 ingresando
   únicamente Email y Contraseña (o Social Sign-In).
2. Auth0 crea la cuenta de credenciales y le asigna el rol base USUARIO.
3. La App realiza el primer login vía PKCE y obtiene el JWT[cite: 1].
4. La App llama a GET /api/users/me[cite: 1]. identity-service ejecuta el JIT Provisioning
   registrando al usuario en user_database con su userId y email únicamente[cite: 1].
   Los campos nombres, apellidos y teléfono quedan vacíos/null.

5.2 Flujo B: Onboarding y Captura Opcional de Datos Personales
Al iniciar sesión con el rol USUARIO
La interfaz presenta dos opciones:

Opción B.1: "Ingresar a un Conjunto" (Ruta a Residente)
1. El usuario selecciona su conjunto e ingresa el número de apartamento.
2. La interfaz permite opcionalmente ingresar o actualizar sus datos personales
   (Nombres, Apellidos y Teléfono). Si el usuario los diligencia, la App envía
   un PUT/PATCH a identity-service[cite: 1].
3. La App envía la SolicitudVinculacion a community-service (estado PENDIENTE
   en community_database)[cite: 1].
4. El Administrador del conjunto revisa la solicitud y presiona "Aprobar"[cite: 1].
5. community-service guarda la relación Residente(userId, conjunto_id, unidad_id)[cite: 1].
6. community-service promueve el rol del usuario a RESIDENTE en Auth0[cite: 1].

Opción B.2: "Registrar un Conjunto" (Ruta a Administrador)
1. El usuario selecciona registrar un nuevo conjunto.
2. El usuario recibe un codigo por correo, al diligenciar el codigo alfanumerico tiene
   derecho a registrar un conjunto(se simula que hizo un pago antes para soliciutar el codigo)
3. Ingresa los datos del conjunto residencial (nombre, dirección, unidades)
   enviando un PUT/PATCH a identity-service[cite: 1].
3. La App envía POST /api/community/conjuntos a community-service.
4. community-service crea el nuevo conjunto residencial en community_database y
   asigna al userId creador como Administrador del conjunto[cite: 1].
5. community-service promueve el rol del usuario a ADMINISTRADOR en Auth0[cite: 1].

*En ninguno de los dos caminos se realizan llamadas síncronas entre community-service e identity-service[cite: 1].*

5.3 Flujo C: Petición Protegida a un Microservicio de Dominio
1. La App Móvil obtiene el contexto del conjunto consultando a community-service
   (GET /api/community/me) tras el login[cite: 1].
2. Para peticiones a servicios como requests-service o security-service, la App
   adjunta el JWT en el header Authorization: Bearer <JWT> y la pertenencia de
   dominio mediante el header X-Conjunto-Id (o mediante sincronización asíncrona
   de eventos con RabbitMQ)[cite: 1].
3. El microservicio destino:
   - Valida la firma del JWT localmente utilizando la clave pública (JWKS) de Auth0[cite: 1].
   - Extrae el userId y el rol del JWT[cite: 1].
   - Verifica el aislamiento por conjunto_id aplicando sus propias reglas de negocio[cite: 1].

6. MATRIZ DE PERMISOS POR ROL
===============================================================================

Rol Global (https://urbanguard.com/rol) | Acceso identity-service | Acceso community-service | Acceso Servicios de Dominio
--------------------------------------------------------------------------------------------------------------------------
USUARIO     | Permite la adición opcional de datos personales al solicitar vinculación o registrar un conjunto[cite: 1] | Registrar un conjunto nuevo O crear SolicitudVinculacion[cite: 1] | Denegado (403 Forbidden) hasta estar vinculado a un conjunto.
RESIDENTE   | Consulta de su perfil personal puro[cite: 1] | Consultar censo, datos de su unidad residencial[cite: 1] | Crear PQRS, solicitar códigos QR de visitantes[cite: 1].
VIGILANTE   | Consulta de su perfil personal[cite: 1] | Consultar directorio de residentes del conjunto[cite: 1] | Escanear códigos QR de ingreso, registrar rondas NFC[cite: 1].
ADMINISTRADOR | Consulta de su perfil personal[cite: 1] | Aprobar/rechazar vinculaciones, gestionar censo[cite: 1] | Consultar reportes de mantenimiento, auditoría de rondas[cite: 1].

===============================================================================
7. ANTI-PATRONES ESTRICTAMENTE PROHIBIDOS
===============================================================================

1. PROHIBIDO almacenar rol o conjunto_id en la tabla Usuario de identity-service[cite: 1].
2. PROHIBIDO realizar llamadas REST síncronas desde microservicios de dominio
   hacia Auth0 o hacia identity-service para validar tokens o resolver identidades
   por cada petición de usuario[cite: 1].
3. PROHIBIDO almacenar contraseñas de usuarios en cualquier base de datos propia
   de UrbanGuard[cite: 1].
4. PROHIBIDO enviar el ID Token de OIDC a los microservicios; las APIs protegidas
   solo aceptan el Access Token (JWT)[cite: 1].
5. PROHIBIDO crear un microservicio backend centralizador para el Dashboard
   Administrativo; la agregación de datos para el dashboard se resuelve mediante
   fan-out cliente en la App Móvil[cite: 1].

8. DECISIÓN DE EQUIPO: SUPERADMIN Y ALINEACIÓN DE CLAIMS (ADR 2026-09)
===============================================================================

8.1 Superadmin de Plataforma (Capa 2.3)
- Adopción: Se adopta formalmente el rol global y marcador de plataforma SUPERADMIN
  por decisión de equipo.
- Separación de capas: El claim https://urbanguard.com/staff (booleano) es
  independiente del claim rol. No se mezclan las capas de negocio y plataforma.
- Identity Provider (Auth0):
  * Marcado manual en app_metadata.platform = "superadmin".
  * Action Post-Login emite el claim staff: true en idToken (leído por la app móvil)
    y accessToken (validado por identity-service).
- Frontend:
  * UserRole incluye SUPERADMIN.
  * Auth0Manager extrae staff del idToken y mapea a UserRole.SUPERADMIN.
  * SessionManager aísla al SUPERADMIN de los conjuntos mock (loadMockAssociations).
  * NavGraph enruta directamente a Routes.ADMIN ("Panel de UrbanGuard Platform").

8.2 Alineación del Claim de Rol (D6)
- Se documenta la re-alineación del custom claim de rol a:
  https://urbanguard.com/rol (emitido por la Action real de Auth0).
  Se mantiene compatibilidad con fallback defensivo hacia https://urbanguard.com/role.
